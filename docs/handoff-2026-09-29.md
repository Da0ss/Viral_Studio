# Viral Studio — состояние перед паузой

Дата: 29 сентября 2026. Работа остановлена по просьбе пользователя до восстановления лимитов.

## Статус

Проект НЕ объявлен готовым к production. Изменения находятся в рабочей директории;
есть изменённые и untracked файлы. Не выполнять reset/checkout/очистку и не считать
все изменения исключительно результатом работы агента. Коммит и deployment не делались
в рамках последних шагов. Реальные файлы Storage не удалялись.

## Что реализовано локально

- Next.js runtime и команды lint/typecheck/test/test:db/test:e2e/build, CI-проверки.
- Auth: безопасные внутренние redirects, проверка пользователя при смене пароля.
- Профиль: сохранение настроек, операции аватара с уникальными путями и CAS,
  защита от устаревших сохранений и честные сообщения об ошибках.
- Проекты: CRUD, поиск/фильтры/пагинация, роли, доступный modal dialog.
  Server Actions используют один Auth-клиент, проверяют UUID, ошибки Auth/ролей,
  возвращают безопасные сообщения при исключениях и неоднозначном результате.
- Onboarding: создание организации и атомарное назначение владельца.
- Чат: отправка, ограниченная история, keyset-пагинация, Realtime catch-up,
  дедупликация и reconnect — локальные/mock-проверки, не живой двухпользовательский тест.
- Уведомления: inbox, пагинация, mark-read и DB producer для сообщений.
  Клиент может изменять только read_at, но не содержание/получателя.
- Материалы: список, поиск/пагинация проектов для загрузки, multipart upload API,
  лимиты тела/файла, whitelist MIME и базовые сигнатуры, скачивание по ссылке на 60 секунд.
- Private Storage: avatars и project-media; RLS на роли/организацию/канонический путь.
- Очистка: private outbox, tombstones, metadata advisory locks, restrictive Storage
  INSERT policy, lease RPC с SKIP LOCKED и token fencing, серверный adapter/core.
  HTTP transport имеет 20-секундные deadlines и сохраняет caller cancellation.
- POST /api/internal/media-cleanup: отдельный секрет, disabled by default,
  одно задание на вызов, no-store и безопасные ошибки. Scheduler не настроен.
- Защита БД: исправление tenant isolation и рекурсивной политики membership;
  ограничения клиентских колонок generation_jobs/notifications/projects;
  отзыв TRUNCATE/REFERENCES/TRIGGER на 11 таблицах; последний владелец;
  неизменяемые membership identities; отзыв project roles при удалении org membership.
- Документы architecture/database/auth/storage/background-jobs/testing,
  production-readiness и исторический implementation-progress.

## На каком шаге остановились

Начато только чтение кода для idempotency создания проекта. Реализация ещё НЕ начата.

Файлы для следующего шага:

- src/actions/projects.ts — createProject сейчас обычный INSERT без request key.
- src/components/projects-client.tsx — ProjectDialog отправляет форму через useActionState.
- tests/unit/project-actions.test.ts — mocks и регрессии действий.
- src/types/projects.ts — схема ввода проекта.

Нужно спроектировать устойчивый ключ отправки, повтор запроса после потерянного
ответа, смену payload, конфликт ключа между пользователями/организациями и reset
ключа только после подтверждённого завершения. Не добавлять обычный upsert, который
может перезаписать чужой или уже отредактированный проект. После дизайна — тесты
повторной отправки, неоднозначного commit и разных payload, затем форма и SQL acceptance.

## Оставшаяся цепочка работы

1. Завершить idempotency создания проекта и проверку формы.
2. Проверить последние миграции на полном disposable Supabase/Postgres stack,
   включая конкурентную смену владельцев, admission/revocation и cleanup leases.
3. Согласовать hosted migration history и разрешённую staging-базу. Ранее remote
   migration операции были отклонены проверкой разрешений; не обходить отказ и
   не трактовать автоматическое продолжение как новое конкретное разрешение.
4. Проверить реальный Storage upload/download/cleanup. Синхронный deleteMedia
   всё ещё удаляет bytes до metadata; UI удаления не подключён. Переключать на
   enqueue-only и включать worker только после acceptance; сейчас он выключен.
5. Завершить загрузки: idempotency, durable reconciliation/orphan cleanup,
   квоты/rate limits, quarantine/scan, совместимость больших файлов с хостом,
   версии и безопасные previews. MIME/signature checks не являются malware scan.
6. Выбрать generation provider/model/budget с пользователем. Не подставлять
   платный провайдер по собственной инициативе. Затем API/UI/job worker,
   cancellation, retries, result persistence и контроль расходов.
7. Реализовать team invitations/roles UI; DB guards уже есть, сама /team — заглушка.
8. Реальные authenticated desktop/mobile E2E: пароль через email, профиль,
   projects/filters, материалы, inbox, двухпользовательский/offline Realtime.
9. Полный security audit, Git history/SSR secrets, CI на hosted runner,
   staging deployment, monitoring, backups и rollback.
10. Повторить всю production acceptance matrix до заявления о готовности.

## Блокеры и предосторожности

- Context7 работал ранее, затем вернул expired OAuth token: нужна повторная авторизация.
- Hosted migration application и authenticated acceptance не завершены.
- Предыдущий hosted проект: sytjbknfwwbombypwfhc; перед работой проверить актуальность.
- Не включать MEDIA_CLEANUP_ENABLED до staging acceptance. Нужен отдельный
  MEDIA_CLEANUP_SECRET, не service-role key, не URL/query и не NEXT_PUBLIC.
- Cleanup RLS не защищает от service-role writes; timeout не доказывает отмену
  удаления на сервере; многосессионная корректность пока не доказана.
- Формальный security scan ранее не завершился: не заявлять, что он пройден.
