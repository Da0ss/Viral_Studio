# Исправление подключённой Supabase: план и журнал

Цель: привести схему `Viral_Studio` в соответствие с уже реализованным бэкендом, сохранив существующие данные. Проект: `sytjbknfwwbombypwfhc`.

## Что подтверждено до изменений

- История содержит 6 миграций, последняя — `20261005202352_production_core_security_and_media_rollout`. Имена ранних миграций отличаются от локальных: весь локальный baseline повторять нельзя.
- Есть 2 пользователя Auth, 2 организации и 2 проекта. Генераций, материалов и версий — 0.
- Отсутствуют upload intents/квоты и их RPC, приглашения и roster RPC, расширенный жизненный цикл генераций/бюджеты/резервы, RPC метрик.
- RLS включён на существующих прикладных таблицах. Закрытая очередь удаления без клиентских политик — предусмотренная граница доступа, а не причина добавлять публичный доступ.
- Снимок определений схемы, ограничений, индексов, политик и прав сохранён в `docs/db-snapshots/hosted-before-2026-10-11.json`. Это снимок схемы, не полноценная резервная копия данных или Storage.

При нерешённой проблеме младшего агента передать конкретный SQL/ошибку GPT‑6 Sol; не повторять один и тот же сбой больше 2–3 раз.

## STEP-BY-STEP

1. **Зафиксировать исходное состояние.** Прочитать историю, колонки, функции, политики, grants и агрегированные количества. Не читать секреты/приватные prompt-данные. Сохранить снимок схемы. Выполнено.
2. **Подготовить точный forward-пакет.** Для каждого нового объекта проверить отсутствие или совпадение существующего определения. Добавить проверки предпосылок; применять изменения атомарно. Существующие таблицы пользователей/проектов не удалять и не сбрасывать. Три пакета подготовлены, независимо проверены и применены.
3. **Загрузки и команда.** Добавить закрытые upload intents, квоты, begin/finalize/reconcile RPC; таблицу приглашений и защищённые create/accept/revoke RPC. Не менять владельцев платформенных таблиц Auth/Storage. Явно ограничить grants и включить RLS.
4. **Генерации.** Добавить lifecycle/lease/idempotency-колонки, закрытые бюджеты/резервы, create/cancel/claim/settlement/reconciliation RPC. Запретить клиентские прямые записи вместо авторизованных RPC. Поскольку jobs=0, перед применением повторно проверить отсутствие legacy jobs; при появлении данных остановить этот пакет и подготовить сохранный backfill.
5. **Версии и roster.** Применить изменения version upload после зависимостей upload/generation; добавить ограниченный roster RPC с проверкой роли вызывающего пользователя.
6. **Метрики.** Добавить service-role-only aggregate RPC. Проверить, что anon/authenticated не могут получить lease, пути, prompts или финансовые строки других пользователей.
7. **Проверить именно подключённую БД.** Выполнить catalog/grant checks, вызов метрик, положительные и отрицательные SQL/RLS/RPC-сценарии в явной транзакции с `ROLLBACK`. Использовать существующие Auth-идентичности, не вставлять искусственные строки в managed Auth. SQL-тесты не отправляют файлы и платные provider requests.
8. **Проверить сохранность.** Сверить исходные количества пользователей, организаций, проектов, материалов и jobs; убедиться, что acceptance не оставил приглашений/резервов/очередей. Проверить миграционную историю и security advisors.
9. **Отдельная проверка приложения.** После схемы проверить сайт с настоящей пользовательской сессией: create/cancel job, version list, upload/finalize/download, команда. SQL-проверка не подтверждает HTTP Auth/Storage/Realtime или работу браузера. Для оплачиваемой генерации отдельно задать бюджет и серверный provider token.

## Условия остановки

- Неожиданные пользовательские данные в таблице, для которой пакет предполагает отсутствие legacy rows.
- Несовпадающий тип/сигнатура существующего объекта, ошибка RLS/grants, отсутствующая зависимость.
- Ошибка применения: сначала проверить, откатилась ли миграция; не повторять DDL вслепую.
- Автоматическое ограничение инструмента или недостаточные права: записать точную причину и завершённые этапы, не обходить блокировку.

## Следующие задачи для исполнителя: маленькие независимые шаги

### A. Настройка Auth — через Dashboard, не SQL

1. Открыть Authentication → настройки паролей проекта `Viral_Studio`.
2. Проверить доступность и условия включения leaked-password protection для текущего тарифа. Не менять тариф автоматически.
3. Если функция доступна, включить защиту. Существующие пользовательские пароли не сбрасывать.
4. Повторно запросить security advisor; критерий готовности — предупреждение `auth_leaked_password_protection` исчезло. [Официальная инструкция](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).

### B. Производительность — отдельная миграция после измерений

1. Из сохранённого `hosted-performance-after-2026-10-11.json` взять 11 FK без покрывающего индекса: `private.generation_output_reservations(project_id)`, `public.asset_versions(created_by)`, `public.assets(created_by)`, `public.audit_log(actor_id)`, `public.messages(parent_message_id)`, `public.messages(sender_id)`, `public.notifications(project_id)`, `public.organizations(created_by)`, `public.projects(created_by)`, `public.team_invitations(invited_by)`, `public.team_invitations(project_id)`.
2. Сверить существующие составные индексы: индекс покрывает FK, если FK-колонки стоят в его начале. Не создавать дубликаты. Для используемых join/delete-путей проверить план запроса на репрезентативных данных; текущие таблицы почти пусты.
3. Подготовить отдельную миграцию выбранных индексов. Если используются `CREATE INDEX CONCURRENTLY`, запускать вне обычной транзакционной миграции; не смешивать два режима исполнения. В первую очередь проверить invitations и generation reservations как новые рабочие пути.
4. Рассмотреть два предупреждения `auth_rls_initplan`: policies `organization_members: owners manage members` и `project_members: project owners manage`. Менять вызовы auth на подзапросы только при сохранении семантики. Прогнать матрицу owner/admin/editor/viewer/outsider до и после; ожидаемые разрешения должны совпасть. [Объяснение оптимизации RLS](https://supabase.com/docs/guides/database/postgres/row-level-security#rls-performance-recommendations).
5. Два предупреждения multiple permissive policies не устранять механическим объединением: permissive-политики суммируют доступ через OR. Сначала зафиксировать разрешённые операции каждой роли.
6. Семь unused-index INFO пока оставить: на небольшой базе отсутствие использования не доказывает ненужность индекса. Готовность — нет дублирующих индексов, права прежние, выбранные рабочие запросы имеют подтверждённый план.

### C. Приложение → API → Supabase → Storage

1. Сверить имена необходимых server-only переменных с `.env.example` и документацией; значения ключей не печатать и не переносить в `NEXT_PUBLIC_*`. Проверить наличие worker/cleanup/reconcile scheduler и их отдельной авторизации.
2. В настоящей сессии owner открыть проект и команду; проверить загрузку roster и версий. Во второй сессии viewer/outsider подтвердить ограничения, в том числе прямые HTTP-запросы к API.
3. Загрузить маленький файл через штатный signed upload, завершить загрузку, скачать и сравнить байты. Создать две версии, проверить номера/порядок/повтор запроса. Удалить родительский материал и дождаться штатного cleanup: только после удаления Storage-объектов квота должна освободиться.
4. Создать и отменить queued generation без обращения к provider; проверить историю, статус и отсутствие оставшихся резервов. Проверить служебные endpoints без секрета/с неверным секретом и с правильным секретом; метрики не должны содержать prompts, пути или персональные данные.
5. Для полного provider-сценария сначала определить разрешённый расход и проверить серверный token. Затем одна небольшая генерация: queued → submitting → running → succeeded, доступный результат, корректное списание/освобождение резерва. При ambiguous provider response не запускать новую платную генерацию вслепую, использовать reconciliation.
6. Проверить обновление интерфейса после фонового завершения через предусмотренный polling/Realtime. Если транспорта обновлений нет, сначала выбрать один способ и описать его отдельной задачей.
7. Критерий готовности этапа C: документировать HTTP-результат каждого сценария и состояние данных/Storage; платный сценарий без фактического запуска отмечать как непроверенный. Не повторять неизменившийся сценарий больше 2–3 раз.

Для задач A/C подходит GPT‑6 Luna; для узкой миграции индексов — GPT‑5.6 Sol. Проверку RLS и неоднозначных worker-сбоев поручать отдельному GPT‑6 Sol при проблеме младшего исполнителя. Дизайн интерфейса вести отдельно: ранее выбранное направление — убрать ощущение шаблонного сайта, сгенерированного ИИ.
